# ENKA Studio — управление каталогом

Подготовлен перенос источника в Supabase и функций Studio в ERP. Он ещё не включён в рабочем окружении; порядок сохранения черновиков и переключения — [CATALOG_SUPABASE.md](../CATALOG_SUPABASE.md).

Текущее рабочее подключение: `https://admin-staging.enkaelectronics.com.ge/` (название адреса осталось прежним, но панель показывает «Рабочий каталог»). Конфигурация — игнорируемый `wrangler.production.local.jsonc`, KV — `STORE_CATALOG`, R2 — `catalog-images`. Для рабочих обновлений используйте именно этот конфиг; `wrangler.local.jsonc` сохраняет прежнюю тестовую конфигурацию. Старая запись через `catalog-api` отключена обёрткой `catalog-api-locked.mjs`, публичные GET сохранены из исходного Worker. Описания и новые страницы требуют привычной ручной сборки магазина.

Панель работает с существующей структурой `catalog.products`. Оригинал остаётся грузинским, переводы RU/EN редактируются отдельно. Неизвестные поля товаров сохраняются. Черновик, история и опубликованный каталог разделены.

Сейчас подготовлены локальная версия и конфигурация нового тестового Worker. Рабочие `catalog-api`, `enka-admin`, `STORE_CATALOG`, `catalog-images` и их домены автоматически не меняются.

## Как пользоваться

1. Найдите товар по названию, SKU, ID или переведённому названию. Нажмите на строку.
2. Во вкладке **Основное** меняйте цены, наличие, грузинские тексты и принадлежность к существующим категориям. ID сохранённого товара защищён: от него зависит адрес страницы.
3. **Фотографии**: загрузите JPG/PNG/WebP или добавьте HTTPS-ссылку. Панель подготовит WebP до 200 КБ. Первая фотография — обложка; стрелки меняют порядок. Удаление фотографии из карточки убирает ссылку, сохраняя сам файл в хранилище.
4. **Характеристики**: грузинские названия и значения. Переводы названий хранятся в общем словаре: исправление одного названия применяется ко всем использующим его товарам.
5. **Русский / English**: введите ручной перевод рядом с оригиналом, проверьте и нажмите **Подтвердить перевод**. Утверждаются только заполненные поля. Автоматического перевода в редакторе нет.
6. **Превью** показывает содержимое карточки на KA/RU/EN. Пока перевод не проверен или его оригинал изменился, отображается грузинский текст. Это превью данных, не готовая страница магазина.
7. **Готово** закрывает карточку, оставляя изменения в текущей вкладке. **Сохранить черновик** сохраняет весь каталог в базе панели. Сайт на этом шаге не обновляется.
8. **Просмотр и публикация** сначала сохраняет изменения, показывает количество добавлений, изменений и удалений. После проверки отметьте подтверждение и опубликуйте. В локальном и тестовом окружениях рабочий магазин не меняется.
9. После будущей рабочей публикации запускайте привычную **ручную сборку магазина**. Цены и наличие читаются из API, а новые страницы, описания и удаление статических страниц требуют сборки.

**Добавить товар** создаёт новую карточку. **Дублировать** копирует товар с новым ID; проверьте SKU и тексты перед сохранением. Варианты цвета/комплектации остаются отдельными товарами.

**История изменений → Восстановить** создаёт новый черновик из выбранной версии. Опубликованный каталог остаётся прежним до отдельной публикации.

**Экспорт** скачивает полный рабочий документ с переводами, включая ещё не сохранённые изменения. **Импорт** принимает этот файл или обычный исходный `catalog` без расширения. Импорт исходного каталога сохраняет существующие переводы; импорт полной резервной копии восстанавливает переводы из файла. Проверка данных выполняется до замены черновика. Фотографии в экспорт не включаются — там только ссылки.

Статусы переводов:

| Статус | Значение |
| --- | --- |
| Нет перевода | Поле ещё не заполнено |
| Нужна проверка | Перевод есть, но не подтверждён |
| Проверено | Перевод подтверждён для текущего оригинала |
| Оригинал изменён | Сохранённый перевод относится к предыдущему тексту; его нужно проверить заново |

Изменение цены или фотографии не сбрасывает проверку текстов. Изменение одного исходного поля затрагивает перевод именно этого поля. Технические числа и латинские обозначения можно оставлять без перевода.

## Локальный запуск

Нужны Node.js 22.13+ и pnpm из `package.json` корня проекта.

Из корня репозитория:

```powershell
pnpm --dir admin install --frozen-lockfile
node admin/dev.mjs --catalog-file "C:\Users\Nick\Downloads\catalog"
```

Адрес: <http://127.0.0.1:4175/>. В текущем рабочем окружении каталог уже скопирован в `.local/admin/seed.catalog.json`, поэтому достаточно `node admin/dev.mjs`.

Первый запуск импортирует файл в новую локальную базу. Последующие запуски открывают сохранённый черновик, не перезаписывая его исходным файлом. Для повторного импорта используйте кнопку в панели.

- `.local/admin/catalog.sqlite` — черновик и история; при работающем сервере рядом могут быть WAL/SHM-файлы.
- `.local/admin/media/` — локально загруженные фотографии.
- `.local/admin/published-kv.json` — имитация опубликованных KV-ключей.
- `.local/admin/published.catalog.json` — совместимый каталог последней локальной публикации.
- `.local/admin/source-catalog-backup-2026-11-05.json` — неизменённая копия предоставленного файла.

Все эти файлы исключены из Git. Перед файловой копией SQLite остановите сервер; для обычной резервной копии каталога используйте **Экспорт**.

Для независимых проверок: `node admin/dev.mjs --port 4177 --data-dir .local/admin-qa`. Остановка сервера: Ctrl+C в его терминале. Локальный режим слушает только `127.0.0.1`; вход Access появится в облачной версии.

## Подключение к Cloudflare: сначала тестовая копия

Для панели не нужен отдельный оплачиваемый сервер. Используются Workers, SQLite-backed Durable Object, KV и R2. Cloudflare предоставляет бесплатные квоты; потребление R2 сверх квоты может оплачиваться. До создания ресурсов проверьте план и расходы в аккаунте: [Durable Objects](https://developers.cloudflare.com/durable-objects/platform/pricing/), [KV](https://developers.cloudflare.com/kv/platform/limits/), [R2](https://developers.cloudflare.com/r2/pricing/).

### 1. Включить вход по коду на почту

Откройте [Cloudflare Dashboard](https://dash.cloudflare.com/) → **Zero Trust**. При первой настройке выберите имя команды и **Free**. Имя создаст адрес вида `https://YOUR-TEAM.cloudflareaccess.com`. Создание организации и подтверждение условий выполняет владелец аккаунта. Cloudflare может потребовать платёжные данные даже для бесплатного плана; это описано в [официальной инструкции](https://developers.cloudflare.com/cloudflare-one/setup/).

Если team domain открывает `/#/NoAuth` и сообщает `Please contact your administrator to enable the Access App Launcher application for your organization`, это означает, что портал App Launcher выключен. Этот портал включается отдельной политикой и не обязателен для прямого входа в админку по её hostname. Team domain без `/#/NoAuth` по-прежнему используется как issuer в конфигурации Worker. [Документация App Launcher](https://developers.cloudflare.com/cloudflare-one/access-controls/access-settings/app-launcher/).

В Zero Trust откройте **Integrations → Identity providers → Add new identity provider → One-time PIN**, если он ещё не добавлен. Затем **Access controls → Applications → Create new application → Self-hosted and private → Add public hostname** (в старом интерфейсе кнопки называются Add an application / Self-hosted):

- Название: `ENKA Admin Staging`.
- Public hostname: `admin-staging.enkaelectronics.com.ge`.
- Защитить весь hostname, включая `/api/*`, `/media/*` и статические файлы; поле Path оставьте пустым.
- Политика: **Allow**, условие **Include → Emails → адрес владельца**. Используйте конкретный email, а не Everyone или весь домен почты.
- Метод входа приложения: **One-time PIN**.
- Сессия, например, 8 часов.

Сохраните приложение и скопируйте его **Application Audience (AUD) Tag**. Для конфигурации понадобятся team domain и AUD: это идентификаторы, не пароль. [Настройка Self-hosted приложения](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/).

Проверка JWT выполняется также самим Worker: подпись, issuer, audience, срок действия и email. Не используйте Bypass для этого приложения. `workers.dev` и version preview URLs в конфигурации выключены.

### 2. Авторизовать инструменты развёртывания

В терминале из корня проекта:

```powershell
pnpm --dir admin exec wrangler login --device
pnpm --dir admin exec wrangler whoami
```

Откроется официальный вход Cloudflare. Режим `--device` подтверждает устройство на сайте Cloudflare и не перенаправляет на `localhost:8976`. Используйте адрес, напечатанный самим Wrangler, и один действующий запрос за раз; старые вкладки входа закройте. Владелец входит и подтверждает разрешения Wrangler в браузере. Пароли, OTP, OAuth-коды и API-токены в чат или файлы проекта не копируются. [Официальная инструкция Device Authorization](https://developers.cloudflare.com/workers/wrangler/commands/general/#use-wrangler-login-without-a-local-callback-server).

### 3. Создать отдельные ресурсы

После входа:

```powershell
node admin/scripts/bootstrap-staging.mjs --catalog-file "C:\Users\Nick\Downloads\catalog" --team-domain "https://YOUR-TEAM.cloudflareaccess.com" --audience "YOUR-STAGING-AUD"
```

Скрипт создаёт **только новые тестовые ресурсы**:

| Ресурс | Имя |
| --- | --- |
| Worker (при последующем deploy) | `enka-admin-v2-staging` |
| KV namespace | `ENKA_ADMIN_V2_STAGING` (Wrangler может добавить префикс) |
| R2 bucket | `enka-admin-images-staging` |
| Тестовый домен | `admin-staging.enkaelectronics.com.ge` |

Создаёт отдельный KV, проверяет его имя через API Cloudflare и импортирует копию исходного каталога. Затем записывает проверочный маркер, который Worker сверяет перед работой с тестовым KV. Информация о выполненных шагах хранится в `.local/admin/cloudflare-staging.json`; её нужно сохранить для продолжения после прерывания.

Результат: `admin/wrangler.local.jsonc`, исключённый из Git. **Если файл уже существует, скрипт его не перезаписывает**: замените team domain/AUD в нём вручную. Сам скрипт Worker не публикует и не переносит локальные SQLite-черновики в облако.

### 4. Проверить и развернуть

Откройте `admin/wrangler.local.jsonc` и проверьте:

- `name` — `enka-admin-v2-staging`.
- `APP_ENV` — `staging`.
- KV — новый тестовый namespace, R2 — `enka-admin-images-staging`.
- `ACCESS_TEAM_DOMAIN` и `ACCESS_AUD` — от тестового Access-приложения.
- `routes` содержит **только** `admin-staging.enkaelectronics.com.ge`.
- `workers_dev: false`, `preview_urls: false`, `run_worker_first: true`.

Затем:

```powershell
pnpm --dir admin exec wrangler deploy --dry-run --config wrangler.local.jsonc
pnpm --dir admin exec wrangler deploy --config wrangler.local.jsonc
```

Откройте <https://admin-staging.enkaelectronics.com.ge>. Сначала должен появиться вход Access, затем панель. Выйдите из Access и проверьте `/api/catalog` в приватном окне: каталог админки не должен выдаваться без входа.

В тестовой панели повторите цикл: изменить товар → сохранить → перезагрузить → проверить переводы → опубликовать → восстановить версию в новый черновик. Загруженные тестовые фото находятся в отдельном R2 и открываются через защищённый `/media/`.

Для переноса локальной работы: **Экспорт** в локальной панели → **Импорт** в облачной тестовой → сохранить черновик. Вместе с экспортом фотографии не переносятся: ссылки `/media/` из локального окружения сначала замените или загрузите фото заново в облако.

## Переход в рабочее окружение — после тестирования

Текущие привязки подтверждены скриншотами владельца:

| Компонент | Рабочее значение |
| --- | --- |
| Публичный Worker | `catalog-api` / `api.enkaelectronics.com.ge` |
| KV binding / namespace | `CATALOG_KV` / `STORE_CATALOG` |
| R2 binding / bucket | `IMAGES_BUCKET` / `catalog-images` |
| Публичные изображения | `https://img.enkaelectronics.com.ge` |
| Старая статическая панель | `enka-admin` / `admin.enkaelectronics.com.ge` |

1. На короткое время остановить изменения в старой панели. Снять свежий экспорт рабочего KV `catalog`, сохранить код/конфигурацию старого API и текущие файлы старой статической панели. Деплой-откат Worker сам по себе не откатывает KV, R2 или базу.
2. Создать отдельный рабочий Worker новой панели с отдельной историей Durable Object и сначала **новым адресом**, например `admin-v2.enkaelectronics.com.ge`. Настроить для него отдельное Access-приложение/AUD.
3. Создать отдельный игнорируемый рабочий конфиг на основе тестового. Сменить name, route, `APP_ENV: production`, Access AUD; привязать рабочие `STORE_CATALOG` и `catalog-images`; задать `PUBLIC_IMAGES_BASE: https://img.enkaelectronics.com.ge`. `ALLOW_PRODUCTION_PUBLISH` пока оставить `false`.
4. Первое открытие загрузит актуальный рабочий каталог в базу новой панели. Не заменять его автоматически старым локальным или тестовым экспортом: после их создания рабочие цены могли измениться. Переносить переводы нужно с проверкой текущего грузинского оригинала. Тестовые ссылки `/media/` запрещены при рабочей публикации.
5. Проверить новую панель в режиме без рабочей публикации. Подготовить переключение старого API на единственного писателя: отключить старые `PUT /catalog` и `POST /upload`, сохранив публичные GET-маршруты. Старую панель закрыть от записи. Одновременное редактирование старой панели/KV и нового черновика может перезаписать изменения.
6. После проверки включить `ALLOW_PRODUCTION_PUBLISH: true`, опубликовать первую рабочую версию, проверить API и запустить ручную сборку магазина.
7. Перенести удобный адрес `admin.enkaelectronics.com.ge` на новый Worker только после проверки резервных копий и новой панели. Обновить Access-приложение/AUD и вернуть вход по почте. Старый Worker сохранить до завершения перехода.

Приложенный `catalog-api-v2.mjs` — **не развёрнутый** вариант публичного API только для чтения. Он сохраняет `GET /catalog`, `GET /v1/feed.xml` и добавляет `?lang=ru|en`, подставляя только подтверждённые актуальные переводы. Для отдельной тестовой проверки предусмотрен `wrangler.catalog-staging.example.jsonc`: подставить новый тестовый KV и отдельный тестовый route. Публичный API не привязывать к защищённому маршруту админки.

Новая публикация сохраняет исходную структуру `products` и дополнительное корневое поле `_enkaPublication`, указывающее на неизменяемую версию переводов. Старые читатели продолжают читать `products`. Сначала записывается версия, затем `catalog`: черновики не выдаются публичным API. После публикации KV может распространиться по регионам с задержкой; при временной недоступности версии переводов используется оригинал.

**Подключение RU/EN ко всем страницам магазина — отдельный следующий этап:** локализованные страницы/словари интерфейса, выбор ручного языка и передача языка сборке/API. Эта панель уже хранит эти переводы, но сама по себе не заменяет Google Translate на текущем сайте. Для прочих языков можно сохранить существующий автоматический перевод.

## Восстановление и ограничения

- В панели: восстановить версию в черновик → проверить → отдельно опубликовать → при необходимости пересобрать сайт.
- При проблеме с новой панелью запретить новые публикации. Восстановление старого интерфейса само по себе не возвращает прежние данные.
- Для аварийного возврата данных использовать сохранённую копию KV `catalog` и при необходимости старый API/сборку; не удалять файлы из R2 во время перехода. Возврат старого записывающего API и общего секрета требует отдельного решения владельца.
- База удерживает последние 50 ревизий, а также исходную и актуальную опубликованную. Регулярный внешний экспорт остаётся полезным, особенно перед массовым импортом.
- Если вкладка сообщает о конфликте: экспортировать свои изменения → загрузить свежую версию → внести нужные правки. Панель не перезаписывает более новый черновик молча.
- Если публикация прервалась: повторить её. Сохранённый журнал продолжит тот же выпуск; перед этим новые сохранения заблокированы. Сообщение об ошибке подтверждения не гарантирует, что публичный KV ещё не обновлён.
- Пока нет редактора структуры категорий: доступны назначения из текущего словаря `public/taxonomy.json`. Массовые операции, автоматическая сборка магазина и перевод интерфейса магазина не входят в эту основу.

## Проверки для разработчика

```powershell
node --test admin/tests/*.test.mjs
pnpm --dir admin exec wrangler deploy --dry-run --config wrangler.example.jsonc
```

Проверяются сохранность структуры исходника, ревизии, конфликты вкладок, транзакционный откат, восстановление, повторная публикация после сбоя, актуальность ручных переводов, подпись JWT и совместимость публичного API. Локальная база и Cloudflare используют один сервис и SQL-хранилище; тестовый сервер не имеет облачных учётных данных.

Фронтенд панели — самостоятельные HTML/CSS/JS. Деплой Worker включает только `public/` и серверный bundle. Jekyll исключает весь `admin/` из сборки магазина; корневой workflow не развёртывает панель автоматически.

## Пакет переводов без замены каталога

`admin/translations/ru-en.json` можно открыть стандартной кнопкой «Импорт». Формат `enka-translation-package` переносит только переводы с совпадающим исходником, сохраняет подтверждённые переводы и импортирует остальные как непроверенные. Товары, цены и фотографии остаются текущими. Полный backup по-прежнему импортируется с заменой документа. Инструкция владельцу: `../TRANSLATIONS.md`.
